# 支付/订单路线图：P6–P10

> 2026-11-21。按「一个 P 是一个完整交付阶段」制定，不再在 P 下切子阶段。
> 每个阶段都可独立上线、独立验收；阶段内只列工作项，不设 P6.1/P6.2。

## 0. 为什么这样排

现有系统已经有相当完整的支付骨架，但缺的是「正确性收口、资金账务、逆向链路、Mock 真实性、运营闭环」。
顺序按风险与依赖排：

```text
P6 交易正确性与安全
      │  （先把状态机、幂等、mock 守卫做对）
      ▼
P7 双分录资金账本与对账
      │  （有了正确交易，才能记清钱和额度）
      ▼
P8 退款与售后逆向
      │  （账本支持借贷，才能做退款冲销）
      ▼
P9 Mock 渠道工程化与故障演练
      │  （用真实回调/查单/退款/账单验证前三个阶段）
      ▼
P10 可观测、沙箱对拍与面试演示
```

不做「先做 UI 再做后端」的拆法：每个阶段都包含该阶段需要的后端、前端、测试和文档。

## 1. 现状盘点

### 已经有的

| 能力 | 位置 |
|---|---|
| 支付单/尝试/事件/发件箱 | `atry-payment`，`t_payment_order/attempt/event/outbox` |
| 支付回调确认、金额校验、事件唯一键 | `PaymentConfirmationService` |
| 支付查单、关单、对账 | `PaymentQueryJob`、`ReconciliationService`、`MockChannelBillProvider` |
| 退款网关能力 | `PaymentGateway.refund()` + `t_refund`（**但没有退款编排/接口**） |
| Mock 签名服务 | `MockSignatureService`（**目前没有被调用**） |
| 商城订单、限购、库存、超时关单 | `MallService`、`MallOrderRepository` |
| 履约幂等（`mall:orderNo`） | `MallFulfillmentService` |
| 额度账本（计量子账） | `t_metering_ledger` |
| 支付/额度指标、审计 | `PaymentMetrics`、`t_admin_audit_log` |

### 必须收口的缺口

1. `POST /api/mall/orders/{orderNo}/mock-pay` 没有生产守卫；生产 `provider=alipay` 时仍可自确认支付。
2. `PaymentConfirmationService` 忽略 `markPaid` 影响行数；关闭/过期支付单回调仍可能写发件箱、履约。
3. `mockPay` 直接调确认服务，绕过真实回调的签名/查单路径；`MockSignatureService` 没被使用。
4. 没有资金侧账本，只有额度子账；无法回答「收了多少现金、发了多少额度、赠送记在哪」。
5. 退款只有网关方法，没有退款单编排、重试、额度扣回和账务冲销。
6. 额度显示成 `¥余额`，商城写「购买」，用户会误认为现金账户。
7. Mock 只覆盖 happy path：没有签名回调、查单、退款、账单、故障剧本。

## P6 — 支付交易正确性与安全（已完成 2026-11-21）

**目标**：让现有交易链路在并发、重复、迟到、关闭、Mock 开关等场景下**不产生错误履约**，并把「充值额度」的语义说清楚。

**状态：已完成**（Mock 守卫、支付/订单 CAS、关闭单回调拒绝、`PAID_AFTER_CLOSE`、重复支付幂等、UI 语义与测试）。

### 交付清单

**安全与入口**
- 新增 Mock 支付访问守卫：仅 `app.payment.provider=mock`、`mock-enabled=true` 且非 `prod` 时开放；
  生产返回 404/403，不暴露入口。
- 生产启动校验：若 `provider != mock` 或 `mock-enabled=false`，任何 Mock 支付 Bean/端点不得注册。
- 对 `createOrder`、`mock-pay` 增加请求级幂等（`Idempotency-Key` 或等价机制），重复提交返回同一结果。

**支付状态机**
- 明确状态与合法迁移：`CREATED → PAYING → PAID / FAILED / CLOSED / EXPIRED`；
  `PAID → REFUNDING → REFUNDED`（P8 使用）。
- 所有状态更新改为 CAS（`WHERE status IN (...)` + 影响行数判断），不再依赖 `if`。
- `PaymentConfirmationService` 检查 `markPaid` 返回 0 的情况：记录 `PAYMENT_CLOSED_AFTER_SUCCESS`、
  告警、拒绝发件箱/履约；进入人工或退款队列。
- 校验 `appId/商户号/币种/金额/订单号`；金额不一致拒绝并告警（金额校验已有，补齐其余字段）。
- 关闭/过期订单收到成功回调：不直接加额度，标记「已收款待处理」，为 P8 退款提供入口。

**订单状态机**
- `CREATED/PAYING/PAID/CLOSED/EXPIRED/REFUNDING/REFUNDED` 全量 CAS；关单只允许从 `CREATED/PAYING`。
- 关闭与支付成功并发：谁先 CAS 成功谁赢；输的一方走「已收款待退款」或「关单失败」分支。
- 库存回补只在 `CLOSED/EXPIRED` 迁移成功时执行一次，不能在回调里重复回补。

**语义与 UI**
- 商城「立即购买」→「充值额度」；顶部「余额」→「当前额度」。
- 商品卡显示：`支付 ¥9.99 · 到账 12.00 额度（含赠送 ¥2.01）`。
- 支付成功显示 `额度 +12.00（支付 ¥9.99）`，不再用「余额增加」表达。
- 订单列表拆分「支付金额 / 到账额度 / 状态」。

**测试**
- Mock 关闭/生产配置 → 端点 404/403。
- 重复 `mock-pay`、重复回调、并发关单与支付、关闭后回调、金额不一致、签名错误。
- 每个测试断言：最多一次履约、额度最多加一次、状态迁移合法。

### 验收标准

- 生产配置下无法调用 Mock 支付；任何路径都不能给关闭/过期支付单履约。
- 同一订单重复支付/重复回调只产生一次额度入账。
- 所有状态迁移有 CAS 与影响行数检查；并发关单/支付有测试。
- 页面明确区分「支付金额、到账额度、赠送额度」。

### 面试价值

幂等三层、状态机 CAS、回调撞关单、Mock 生产隔离、请求重试。

### 规模与依赖

中大型；无前置阶段。会改 `MallController/MallService`、`PaymentConfirmationService`、支付/订单仓储、前端商城页。

## P7 — 双分录资金账本与额度对账（已完成 2026-11-21）

**目标**：把「收到的钱」和「发出的额度」分开记账，做到每笔交易借贷平衡、用户额度可对账、日终可发现差异。

**状态：已完成**（V903/V904、双分录记账点、OPENING_EQUITY 期初回填、sweep 兜底、日终快照、管理端汇总页）。
实测负债=计量余额、清算=已付订单、借贷不平 0。

### 交付清单

**账本模型（chatry 资金域）**
- `t_fund_ledger_account`：账户编码、类型（ASSET/LIABILITY/REVENUE/EXPENSE）、归属用户、币种、正常方向。
- `t_fund_ledger_transaction`：业务类型、业务单号、事件唯一键、发生时间、描述。
- `t_fund_ledger_entry`：交易 ID、账户、方向、金额（`DECIMAL(20,6)`）、币种。
- 账户至少：`PSP_CLEARING`、`CREDIT_LIABILITY:<userId>`、`REVENUE`、`PROMO_EXPENSE`、`REFUND_PAYABLE`、`OPENING_EQUITY`。
- 约束：同一 transaction 借贷合计相等；事件唯一键幂等；所有金额正数，方向表达借贷。

**记账规则**
- 充值成功：借 `PSP_CLEARING`（实付）、借 `PROMO_EXPENSE`（赠送）、贷 `CREDIT_LIABILITY`（到账额度）。
- 新手赠送：借 `PROMO_EXPENSE`、贷 `CREDIT_LIABILITY`。
- 对话消费：借 `CREDIT_LIABILITY`、贷 `REVENUE`（按实际结算金额）。
- 退款（P8）：借 `CREDIT_LIABILITY`（未消费部分）、贷 `PSP_CLEARING`；已消费部分按退款政策。
- 历史数据迁移：用 `OPENING_EQUITY` 做期初平衡分录，按现有 `t_metering_ledger` 余额回填，禁止账本从「凭空余额」开始。

**集成**
- 支付成功事件消费：在 `MallFulfillmentService` 同一本地事务里完成额度入账 + 资金分录 + 订单 PAID。
- 对话结算：由 metering 结算事件驱动（事件键 `settle:llm:<requestId>`），资金域幂等消费，补收入分录。
- 保留 `t_metering_ledger` 作为额度子账；资金总账与子账通过业务单号/事件键关联，不重复记账。

**对账与运营**
- 日终对账任务：支付单已收款 vs `PSP_CLEARING`；用户额度余额 vs `CREDIT_LIABILITY`；渠道账单（复用现有 `ReconciliationService`）。
- 差异表 + 告警；管理端新增「资金账本/对账」页面（试算平衡、账户余额、差异列表）。
- 指标：借贷不平数、对账差异数、账实差异金额。

**测试**
- 每笔 transaction 借贷相等（属性测试/遍历校验）。
- 重复支付事件、重复结算事件不重复记账。
- 赠送、退款、部分退款场景账本平衡。
- 对账正常场景差异为 0；构造差异能被发现。

### 验收标准

- 所有资金交易借贷平衡，任意时点 `sum(debit)=sum(credit)`。
- 用户额度余额与 `CREDIT_LIABILITY` 逐用户一致。
- 日终对账能输出「平/差异」，差异可定位到业务单。
- 管理端能查看账户余额和差异，不直接改账。

### 面试价值

预付费负债、收入确认、赠送成本、双分录、账实一致、对账差异处理。

### 规模与依赖

大型；依赖 P6 的稳定事件与状态机。新增迁移、资金域模块、管理页面。

## P8 — 退款与售后逆向链路（已完成 2026-11-21）

**目标**：让退款成为一条完整、幂等、可对账的逆向链路，而不是只有网关方法。

**状态：已完成**（RefundService/RefundOperations、部分退款、退避重试、额度扣回、REFUND_PAYABLE、
关单后自动退款、`/admin/refund` 页面）。

### 交付清单

**支付域退款编排**
- 新增 `RefundService`：创建退款单、校验支付单 `PAID`、金额不超过「实付 - 已退」、退款单号/幂等键唯一。
- 状态机：`CREATED → REFUNDING → SUCCESS / FAILED`；失败退避重试，超过次数进人工。
- 调用 `PaymentGateway.refund()`，记录渠道退款号；重复请求返回同一退款单。
- 提供用户申请（或管理员发起）与退款查询 API；后台任务处理 `REFUNDING`。

**业务侧冲销**
- 退款成功事件 → 商城订单 `REFUNDED`；扣回未消费额度，按比例冲销赠送（`PROMO_EXPENSE` 反向）。
- 额度不足策略必须明确：推荐「只退未消费部分，已消费不退」或「允许负额度 + 冻结账户」，二选一写进配置和文档。
- 资金账本记退款分录；对账包含退款。
- 退款失败/部分成功要可查询、可重试、可人工处理。

**展示与测试**
- 订单详情显示退款状态、退款金额、退款时间；管理端退款列表。
- 测试：重复退款、部分退款、已消费退款、渠道失败重试、退款后额度/账本/对账一致。

### 验收标准

- 退款金额不能超过可退金额；重复请求不重复退。
- 退款成功后额度、订单、资金账本、对账四处一致。
- 渠道退款失败可重试且不产生重复退款。

### 面试价值

退款幂等、部分退款、已消费额度、逆向记账、状态机补偿。

### 规模与依赖

中大型；依赖 P7 的账本账户与分录能力。

## P9 — Mock 渠道工程化与故障演练（已完成 2026-11-21）

**目标**：把 Mock 从「一个确认按钮」升级成「可控的假 PSP」，让 P6–P8 的失败路径可以被稳定复现和自动化验证。

**状态：已完成**（签名回调真链路、8 个故障剧本、开发台接口与页面、chatry 收银台接入、8 个集成用例）。

### 交付清单

**Mock 渠道能力**
- Mock 收银台/确认接口走真实链路：生成渠道流水 → 签名回调 → `PaymentCallbackService.acceptVerified`；不再直接调确认服务。
- 使用现有 `MockSignatureService`（HMAC/RSA）签名；服务端验签，签名错误拒绝。
- 实现 Mock 查单、关单、退款、渠道账单（账单可复用/扩展现有 `MockChannelBillProvider`）。
- 回调异步化：可配置延迟、重试、重复投递；支持乱序。

**故障剧本**
- 场景：成功、失败、超时、重复回调、延迟回调、乱序、金额错、签名错、关单后回调、退款失败、退款重复。
- 触发方式：按订单配置/请求头/开发控制台；只允许 dev/test。
- 场景执行有指标与日志，便于演示和回归。

**测试与隔离**
- 集成测试矩阵覆盖全部剧本；契约测试保证 Mock/Alipay 实现同一 `PaymentGateway` 语义。
- 生产启动禁止 Mock 端点；CI 中 Mock 场景测试跑在测试 profile。
- 文档：Mock 能力边界、如何切换真实渠道、哪些差异必须沙箱验证。

### 验收标准

- 一条命令/页面能触发重复、延迟、金额错、关单后回调等场景。
- 所有场景通过真实回调/查单/退款路径，业务代码无特判。
- 生产配置下 Mock 端点不存在；测试环境可完整回归。

### 面试价值

渠道抽象、回调验签、故障注入、支付测试策略、Mock 与生产差异。

### 规模与依赖

中大型；依赖 P6–P8 的接口与事件。

## P10 — 可观测、运行手册与面试演示（已完成 2026-11-21）

**目标**：把支付系统变成「可运营、可证明、可讲清楚」的完整案例。

### 交付清单

**可观测**
- 支付看板：成功率、失败原因、回调延迟/重复、掉单数、卡单数、退款积压、对账差异、账本不平数、Mock 场景计数。
- 告警：支付成功率骤降、回调失败率高、`PAYING` 超时、对账差异 >0、账本不平、退款失败。
- 运行手册：掉单、重复回调、关单后支付、退款失败、对账差异、账本修复（只允许冲正，不直接改余额）。

**不做的部分**
- 不与真实支付渠道做对拍：本项目定位是 mock 支付内核，真实网关由其独立项目验证；
  P10 只验收本系统自身的可观测、告警、运维与演示能力。

**演示与面试材料**
- 5 分钟演示脚本：正常充值 → 重复回调 → Mock 关闭 → 关单后回调 → 退款 → 对账/账本。
- 架构图、状态机图、时序图、关键取舍（outbox vs 2PC、预付费负债、Mock 边界）。
- 面试问答卡片：把 P6–P9 的实现映射到「幂等/掉单/对账/退款/一致性」问题。

### 验收标准

- 看板能实时看到支付/回调/退款/对账/账本指标，告警可触发。
- 运行手册覆盖卡单/重复回调/关单后支付/退款失败/账实差异/发件箱积压六类处置。
- 演示脚本可在本地一键跑通，覆盖至少 5 个失败/恢复场景。
- 文档能支撑 30 分钟支付系统面试讲解。

### 面试价值

生产运维、监控告警、对账、故障处理、方案取舍表达。

### 规模与依赖

中型；依赖 P6–P9。

## 2. 阶段依赖与交付节奏

| 阶段 | 核心交付 | 依赖 | 规模 |
|---|---|---|---|
| P6 | 状态机/幂等/Mock 守卫/UI 语义 | 无 | 中大型 |
| P7 | 双分录资金账本 + 对账 | P6 | 大型 |
| P8 | 退款/售后逆向 | P7 | 中大型 |
| P9 | Mock 假 PSP + 故障剧本 | P6–P8 | 中大型 |
| P10 | 可观测/沙箱/演示 | P6–P9 | 中型 |

每个阶段结束都必须满足：**代码 + 迁移 + 测试 + 文档 + 可演示**，不把测试/文档留到下一阶段。

## 3. 跨阶段不变式（任何阶段都不能破坏）

1. 生产环境不存在可用的 Mock 支付入口。
2. 一笔支付最多履约一次，额度最多入账一次。
3. 回调金额与支付单金额不一致时绝不入账。
4. 所有状态迁移必须 CAS + 影响行数检查；禁止 `if (status == ...) update`。
5. 资金账本每笔交易借贷相等；禁止直接改余额，只允许冲正分录。
6. 任何「支付成功」都必须能被渠道查单/账单/对账证实。
7. 退款、重复回调、掉单、关单后支付都有自动化测试和人工处置入口。

| 下单/支付/加额度三库一致性？ | P6/P7 |
| 钱和额度怎么对账？赠送怎么记账？ | P7 |
| 退款重复、部分退款、已消费额度？ | P8 |
| 回调丢了、重复、乱序、金额错，怎么测？ | P9 |
| 怎么发现资损、怎么告警、怎么修复？ | P10 |

## 5. 建议的开工顺序

先做 **P6**：它是所有后续阶段的地基，且能立刻修掉「生产可自确认支付」「关闭单仍履约」两个高危问题。
